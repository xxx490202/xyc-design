MCP servers

Nine small instruments on one bench: ask, browse, remember, schedule, consult, drive the desktop, capture the screen, read the materials, read the other pages.

Nine servers stdio JSON-RPC Python 3.10+ Runs beside Quanta v1.0.0

01 · SkillSkills 02 · PluginPlugins 03 · ConnectorConnectors 04 · MCPMCP servers
What an MCP server is

A small program on the other end of a pipe.

Each server here is a short Python program speaking stdio JSON-RPC: one JSON object per line, stdout kept JSON-only so nothing but protocol ever goes out. Quanta starts it, reads its tool list, and calls a tool like any other step in a turn.

They import Quanta's config and read the app data directory, so they run beside a Quanta checkout rather than as standalone services. That is both a constraint and the point: the server sees the same files, memory and pages the app does.

One line, one message

No framing, no length prefix, no HTTP. A newline is the boundary; a stray print breaks the pipe.

Small on purpose

Each server does one thing and exposes a few tools. When one misbehaves, you can read the whole file in a minute.

Reads the app's data

Memory notes, scheduled runs, page outputs and materials are read from the same directory the window uses.

MCP-01quanta-ask

When the answer is not in the model.

Some decisions are not the agent’s to make: which folder, which account, which of two nearly identical files. quanta-ask turns that moment into a card in the window — a few options, one choice — and holds the turn until a person answers.

  • The turn waits No default, no guess, no answering its own question. The tool returns when the card does.
  • Selection, not free text Options come from the caller, so the answer is always something the code can act on.
  • It stays in the transcript Question and answer remain in the thread, where the next turn can read them.
Download · zip quanta-ask.zip
MCP-02quanta-browser

A tab the agent can actually see.

Quanta’s browser is a real tab inside the window, not a headless browser in a container. quanta-browser drives that tab — open a URL, click a link, read the page — and what it read stays on screen where you can check it.

  • The tab you can see No second, invisible browser with its own cookies and its own version of the page.
  • Read, then quote The text comes back as content, so an answer can point at what is on screen.
  • Closing ends it No background automation is left running after the turn.
Download · zip quanta-browser.zip
MCP-03quanta-memory

Remembering is a file operation.

The memory store is a folder of Markdown notes with frontmatter, filed by area. quanta-memory is how a turn touches it: save a note, search by meaning, read one back, link two together, list what is there.

  • Plain files Every note opens in any editor, and the folder can go into git.
  • Filed by area Notes sit under the page they came from, not in one undifferentiated pile.
  • Tools, not stuffing save · search · read · link · list are calls the agent makes, not context pasted in.
Download · zip quanta-memory.zip
MCP-04quanta-schedule

Work that happens while the window is closed.

Scheduled runs are how Quanta keeps working when nobody is watching. quanta-schedule lists them, switches them on and off, and can start one immediately — the same entries that appear on the Scheduled page.

  • Cron, not alarms Recurring work is a schedule with an owner, not a one-off reminder.
  • The same sandbox A run gets the tools and the folder the session already had; being unseen widens nothing.
  • A run leaves a record Output lands on the page it belongs to, so the next turn can read it.
Download · zip quanta-schedule.zip
MCP-05quanta-harness

A second opinion, on demand.

When a decision is expensive, one model’s opinion is not enough. quanta-harness puts the same question to Claude Code, Codex or DeepSeek as consultants — separate contexts, no edits — and brings their answers back to the main thread, which still decides.

  • Consultants, not delegates They answer the question and return. The plan stays where it was.
  • Separate contexts Each consultant gets the question, not your whole history.
  • Disagreement is the output Two objections are worth more than three agreements, and the transcript keeps both.
Download · zip quanta-harness.zip
MCP-06quanta-cua

Hands on the desktop.

Some work only exists as a desktop app with no API. quanta-cua moves the pointer, clicks, types, and then looks at the screen to see whether it worked — through @trycua/cua-driver, on your machine.

  • Move, click, look The loop is not optional: every action is followed by a look at what it did.
  • Needs a driver @trycua/cua-driver, plus QUANTA_DATA_DIR and QUANTA_CUA_ROOT.
  • Your desktop, your risk It can press anything you can press, which is why the permission prompt stays in the way.
Download · zip quanta-cua.zip
MCP-07quanta-screen

When it can only look, not touch.

When the driver is missing — another machine, a locked-down system — quanta-screen is the smaller promise: take a screenshot, crop what matters, and hand the image to the model. Look, but do not touch.

  • Fallback by design It exists so a machine without the driver still has eyes.
  • Crop before sending A window crop is smaller and more legible than a whole desktop.
  • No input A screenshot cannot click. If the task needs a click, it needs cua.
Download · zip quanta-screen.zip
MCP-08quanta-materials

The files are the evidence.

A project’s materials — PDFs, spreadsheets, notes, figures — are read through this server, then judged: does this cover the claim, is there evidence, does the context hold. The files stay where they are.

  • List and read No import step and no copy into a database; the folder is the source.
  • Judgments, not summaries jev judgments ask whether the material supports something, not what it says.
  • Page-scoped Materials belong to a project, and the judgments are about that project’s claims.
Download · zip quanta-materials.zip
MCP-09quanta-pages

One page reads another.

Each page in Quanta produces something: a plan, a chart, a crawl log, a sentiment read. quanta-pages lets a turn read what another page produced, so work done in one room can be used in the next.

  • Read, not drive It reads another page’s output; the page that produced it stays in charge of it.
  • Outputs are dated An output knows when it was written, which is how a turn tells fresh from stale.
  • One working folder Pages share files, so reading an output is not a copy of it.
Download · zip quanta-pages.zip
Running

Started per session, spoken to in lines.

Quanta spawns a server, sends JSON on stdin, reads JSON on stdout. There is no port, no handshake to configure and nothing left running after the session ends.

Install

Unzip beside the app, register, done.

  1. 01Unzip into the mcp folder. One folder per server, next to the Quanta checkout — the imports expect the app's config module.
  2. 02Run it once by hand. python3 ask_tools.py. If it starts and waits on stdin, the pipe is fine.
  3. 03Register it in Quanta. Add the command to the MCP list; the server's tools join the turn's tool list.
$ unzip quanta-ask.zip -d mcp/
$ python3 mcp/quanta-ask/ask_tools.py
# waiting on stdin — one JSON object per line

$ export QUANTA_DATA_DIR="$HOME/Library/Application Support/Quanta"
$ export QUANTA_CUA_ROOT="$HOME/.quanta/cua"   # cua only

# register (Quanta → Settings → MCP)
{ "command": "python3", "args": ["mcp/quanta-ask/ask_tools.py"] }

The CUA server is the one with a real dependency: @trycua/cua-driver. Without it, quanta-screen is the fallback — a screenshot and nothing more.
